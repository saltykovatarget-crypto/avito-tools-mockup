## ГДЕ ТЫ ПРАВ (фиксируем как решение)

### 1. curl_detail как primary — верный приоритет
У тебя есть production-факт: curl detail отдаёт нужные markers на 5/5 URL. Не бросаем рабочий curl ради переписывания на Playwright. Правильно.

### 2. «Не делать хаотичную ротацию User-Agent» — тут ты грамотнее документа
Это тонкий момент. Постоянная смена UA/браузера внутри одной сессии — красный флаг для анти-бота: реальный человек не меняет браузер каждые 5 минут. Принцип «один аккаунт = один proxy = один стабильный профиль = один UA» — правильный.

Уточнение по документу: пример с `random.choice` в скрипте прогрева — это про выбор разных **поисковых запросов** и про разные **аккаунты**, а не про ротацию UA внутри сессии. Так что противоречия нет, твой принцип в силе.

### 3. Мобильный API Avito — в отдельный R&D
Согласна. В документе он сам помечен как «структура может меняться». Смешивать экспериментальный путь с production — риск. Выносим в отдельный тест.

## ТРИ УТОЧНЕНИЯ (важно зафиксировать)

### Уточнение 1 — тест на 50 URL должен мерить не только «прошло/не прошло»

Авито банит не за один запрос, а за **паттерн во времени**. curl может пройти 50 URL сегодня и упереться в капчу на 200-м запросе завтра.

Поэтому при тесте на 50 URL смотри не только success rate, но и:
- появляются ли софт-капчи ближе к концу прогона;
- нет ли ответов `429 Too Many Requests`;
- не деградирует ли качество ответа (обрезанный HTML, отсутствие markers) к концу серии.

И главное — реальная проверка это **не 50 URL за один раз, а нагрузка во времени**: 30 парсингов в день × 5-7 дней подряд. Если за неделю нет капч и деградации — тогда curl_detail подтверждён для production.

### Уточнение 2 — fallback не откладывать до момента поломки

curl-путь не вечен. Авито периодически усиливает защиту. Когда (не «если») curl начнёт ловить challenge — нужен готовый fallback, иначе сервис встанет в тот же день.

Ты держишь Playwright + Xvfb в плане C — правильно. Просьба: не доводить план C до состояния «начнём писать когда сломается». Иметь хотя бы минимальный рабочий browser-fallback заранее, пусть медленный и на 5% запросов. Лучше готовая страховка чем простой сервиса.

### Уточнение 3 — AccountPool это страховка, а не «когда-нибудь потом»

Согласна что AccountPool + мобильные прокси — этап после MVP. Но формулировку «стратегическое усиление после MVP» давай уточним: это не «приятный бонус на будущее», а **страховка которую надо успеть построить до того как Авито закрутит гайки**, а не после.

Порядок такой:
1. curl_detail MVP → подтвердить на недельном тесте;
2. параллельно — минимальный browser-fallback (Playwright+Xvfb) наготове;
3. AccountPool + мобильные прокси — следующий этап, но не «потом когда-нибудь», а с конкретным сроком после подтверждения MVP.

## ИТОГОВАЯ АРХИТЕКТУРА (принято)

```
listing:          curl
detail:           curl_detail (primary)        ← приоритет
photos:           из listing/detail HTML
browser:          limited fallback only
Playwright+Xvfb:  замена Selenium-fallback на этапе C
                  (минимальная версия — наготове заранее)
AccountPool:      усиление после MVP
                  (со сроком, не «когда-нибудь»)
мобильный API:    отдельный R&D, вне production
```

Принцип стабильности: один аккаунт = один proxy = один стабильный профиль. Без хаотичной ротации.

## ЧТО ОТ ТЕБЯ ЖДУ ПО ИТОГУ

1. Реализуй curl_detail backend как primary (план B.2).
2. Прогони недельный тест (30/день × 5-7 дней), смотри на капчи/429/деградацию, не только на success rate.
3. Держи минимальный Playwright+Xvfb fallback наготове, не откладывай в долгий ящик.
4. После подтверждения MVP — назови срок на AccountPool + мобильные прокси.

Если по ходу что-то всплывает — пиши сразу, не молчи.
