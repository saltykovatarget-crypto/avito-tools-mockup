## 🤔 Зачем интегрироваться с Авито-аккаунтами клиентов

### Use-cases, которые откроет интеграция

| Сценарий | Сейчас (manual) | После интеграции |
|---|---|---|
| Анализ статистики | Юзер выгружает XLS из Авито и грузит сам (50 ₽) | Автозагрузка стат каждый день |
| Мониторинг позиций | Юзер вводит ID + город каждый раз (99 ₽) | Авто-мониторинг 24/7 + алерты в TG |
| Управление объявлениями | Юзер сам идёт в Авито и правит | Правка прямо у нас в кабинете |
| Бид-менеджер | Юзер сам корректирует ставки | Авто-оптимизация ставок |
| Ответы клиентам Авито | Юзер в Авито-приложении | Ответы прямо в нашем чате |
| Активация AI-Продавца | Сложно для юзера | Включил тумблер → AI отвечает за тебя |

### Что это даёт бизнесу

- **+30–50% к LTV** — клиент глубже интегрирован, реже отваливается
- **Premium-фичи** — можно брать выше за «полную автоматизацию»
- **Барьер для ухода** — клиент не уйдёт к конкуренту, если у нас стоят его аккаунты
- **Конкуренция с B2BHELP** — у них автоматизация это ключевое УТП, мы добавляем своё + методология

## 🚧 Варианты интеграции (от простого к сложному)

### 🟢 Вариант A — OAuth от Авито (если будет публичный API)

**На 2026-06**: у Авито нет публичного OAuth для B2B (только для крупных партнёров с подписанным договором).

**Если Авито откроет**: это идеальный путь — стандартный OAuth2, токены, scope'ы, наш сервер общается с их API.

**Архитектурно:**
- Таблица `avito_oauth_tokens` (refresh_token, access_token, scopes, expires_at)
- Сервис `AvitoOAuthService` для обмена токенов
- Фоновый воркер для refresh

---

### 🟡 Вариант B — Cookie-based session relay (быстрый старт)

Юзер логинится в Авито в своём браузере → **наш браузер-расширение** забирает cookies → отправляет нам → мы делаем запросы от его имени.

**Плюсы:**
- Работает уже сегодня (без API Авито)
- Юзер контролирует доступ (может отозвать через расширение)

**Минусы:**
- Cookies живут 1–2 недели, потом юзер должен «обновить связь»
- Если Авито меняет внутренний API → ломается
- **Серая зона** в TOS Авито (хотя B2BHELP, AvitoMaster и aiavi делают так)

**Архитектурно:**
- Таблица `avito_sessions` (user_id, cookies_encrypted, expires_at, account_label)
- Сервис `AvitoSessionService` (расшифровка, HTTP-запросы с сессией)
- **Сессии шифруются на стороне сервера** (AES-256 + ключ из ENV)
- Расширение Chrome/Firefox — отдельный mini-проект
- Endpoint: `POST /api/avito/connect` (юзер пришёл из расширения с cookies)

**Это вариант, который реально использует B2B-Help, AvitoAI и т.д.**

---

### 🔴 Вариант C — Headless Chrome за юзера (тяжело)

Мы держим в облаке headless Chrome, юзер логинится в нашем UI → мы сохраняем сессию → дальше работаем как «он».

**Плюсы:**
- Полный контроль
- Юзеру не нужно ставить расширение

**Минусы:**
- Дорого по инфре (1 контейнер на юзера)
- Risk: Авито банит IP если массово
- 2FA / Капча ломают флоу

**Не рекомендую** для нашей фазы.

## ✅ Что нужно заложить в архитектуру СЕЙЧАС

Чтобы потом не переписывать, **уже в MVP** учесть следующее:

### 1. Сущность «Avito-аккаунт» отдельно от User

Один юзер = N аккаунтов Авито (агентство может вести 10 клиентов).

```sql
-- Добавить в Phase 1 или Phase 6, даже если пустая таблица:
CREATE TABLE avito_accounts (
  id BIGSERIAL PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id),
  label VARCHAR(100),                    -- "Мой основной", "Клиент Иванов"
  avito_user_id BIGINT,                  -- ID на стороне Авито
  connection_type VARCHAR(20),           -- 'manual' | 'cookie' | 'oauth'
  status VARCHAR(20) NOT NULL DEFAULT 'manual',  -- manual / connected / expired / banned
  -- зашифрованные данные для cookie/oauth (NULL пока вариант manual):
  encrypted_credentials BYTEA,
  expires_at TIMESTAMP,
  last_synced_at TIMESTAMP,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_avito_accounts_user_id ON avito_accounts(user_id);
```

**На MVP**: `connection_type = 'manual'`, `encrypted_credentials = NULL`. Сущность просто фиксирует «юзер ассоциировал свой Авито-кабинет с нашим аккаунтом». Запись создаётся при первом действии связанном с конкретным Авито-аккаунтом (например когда юзер запускает парсер на свою выдачу).

### 2. Все действия привязаны к `avito_account_id` (не только к `user_id`)

```sql
-- При создании таблиц следующих сущностей добавить FK:
ALTER TABLE parser_runs ADD COLUMN avito_account_id BIGINT REFERENCES avito_accounts(id);
ALTER TABLE position_checks ADD COLUMN avito_account_id BIGINT REFERENCES avito_accounts(id);
ALTER TABLE xls_analyses ADD COLUMN avito_account_id BIGINT REFERENCES avito_accounts(id);
-- + любые другие "действия над Авито-аккаунтом"
```

**Зачем сейчас:** даже если в MVP у юзера только один аккаунт, через 3 месяца агентства захотят вести 5+ клиентов в нашем кабинете. Если не заложить FK — придётся мигрировать историю по большому количеству записей.

### 3. Service-layer абстракция

В коде создаём интерфейс, реализуем пока `ManualAvitoService` (просто берёт URL/ID от юзера). Потом подменяем на `CookieAvitoService` или `OAuthAvitoService`.

```python
# backend/app/services/avito/__init__.py
class AvitoServiceProtocol(Protocol):
    """Контракт для работы с Авито-аккаунтом юзера."""
    
    async def fetch_stats(self, account_id: int, period: tuple[date, date]) -> dict:
        """Получить статистику кабинета."""
        ...
    
    async def get_listings(self, account_id: int) -> list[dict]:
        """Список объявлений."""
        ...
    
    async def update_listing(self, account_id: int, listing_id: str, fields: dict) -> dict:
        """Обновить поле объявления."""
        ...
    
    async def check_positions(self, account_id: int, listing_ids: list[str], city: str) -> list[dict]:
        """Проверить позиции."""
        ...

# В MVP — заглушка:
class ManualAvitoService:
    """Юзер сам предоставляет данные. Для MVP."""
    
    async def fetch_stats(self, account_id: int, period: tuple) -> dict:
        raise NotImplementedError("Загрузи XLS вручную")

# Когда будет интеграция:
class CookieAvitoService:
    """Работает через cookies от юзерского расширения."""
    async def fetch_stats(...): ...  # реальная имплементация
```

**Зачем сейчас:** код, использующий `AvitoService`, не будет знать что внутри. Это позволит подменить реализацию без переписывания всех эндпоинтов.

### 4. UI: место под «Подключить аккаунт» в кабинете

На странице кабинета добавить **disabled-карточку**:

```
┌─────────────────────────────────────────┐
│ 🔌 Подключить аккаунт Авито             │
│ (Скоро — позволит автозагружать         │
│  статистику и управлять объявлениями)   │
│                                          │
│ [Уведомить меня когда будет готово]    │
└─────────────────────────────────────────┘
```

**Зачем сейчас:** юзеры **видят, что мы это сделаем**, не уходят к B2BHELP. Кнопка «Уведомить» собирает интерес → видишь когда есть спрос → решаешь когда делать.

### 5. Списания за «авто-действия» — заложить новые цены

Когда придёт интеграция, появятся **периодические действия** (раз в день / раз в час). Это другая ценовая модель — **подписка на функцию**, а не разовая плата.

Например:
- «Авто-мониторинг позиций» — 99 ₽/мес (вместо 99 ₽ за разовую проверку)
- «AI-Продавец» — 990 ₽/мес (отвечает клиентам 24/7)
- «Авто-XLS» — 290 ₽/мес (стат подгружается каждый день)

**Заложить в `pricing.py`** уже сейчас отдельный класс/enum для подписок на функции, даже если он пустой:

```python
class FeatureSubscription(Enum):
    POSITION_MONITOR_MONTHLY = 9900    # 99 ₽/мес — позже
    AI_SELLER_MONTHLY = 99000          # 990 ₽/мес — позже
    XLS_AUTO_MONTHLY = 29000           # 290 ₽/мес — позже

# таблица user_feature_subscriptions — добавить позже
```

⚠️ **Это не противоречит wallet-модели**: вместо «подписки на тариф» это **подписки на ФИЧИ** через кошелёк (списывается раз в месяц с баланса). Прозрачно для юзера: «эта фича стоит 290 ₽/мес, кошелёк → списание раз в месяц → можно отключить в любой момент».

## 🚨 Что точно НЕ делать

❌ **Не делать «авто-отвечалку»** в стиле B2BHELP-автоответа на keywords. Это пошлая фича, у клиентов будет ощущение «бот тупо отвечает». Если делаем — только полноценный AI-Продавец на GPT.

❌ **Не делать «накрутку поведенческих факторов»** (просмотры, избранное). Это серая зона, нарушает TOS Авито, портит репутацию.

❌ **Не делать «автоматическое размещение» через XML/конструктор** на R2. Сначала валидируем спрос, потом делаем.

❌ **Не лочить интеграцию в дорогой тариф**. В wallet-модели — фичи через подписки на ФИЧИ (290 ₽/мес), а не через закрытие за платным тарифом. Иначе теряем философию «платишь только за то, что используешь».

## 📞 Решение о запуске интеграции

**Когда делать R2 (cookie-based интеграция)?**

Триггер: **первые 100–200 платящих юзеров** → у них есть критический спрос на автоматизацию → видно по поведению (часто запускают парсер, проверку позиций руками).

До этого момента — **manual через UI** работает. Не тратим время на сложную интеграцию пока не доказали базовый спрос.
